The Order Router

A complete, line-by-line walkthrough of both scripts running this storage system: the master LuaController and its companion signal filter — how they track thousands of items and fulfil requests from a touchscreen or a written book inside a 100,000-byte memory budget.

master.lua + signal_filter.lua · mesecons_luacontroller · digilines
01

The system, at a glance

Two scripts, two LuaControllers. master holds every byte of persistent state and makes every decision. signal filter holds nothing — it exists purely so master doesn't get a separate event for every single chest in a large array.

touchscreen→ Take→ book order→ queued pull→ final chest→ delivered

One fact governs almost every line in both files: a LuaController re-runs its entire script, top to bottom, on every single event it receives. Only the mem table survives between events — every local variable and every function is rebuilt from nothing, every time. Nothing below makes sense without that in mind.

02

Persisted state

The whole file opens with the same shape repeated: if not mem.X then mem.X = ... end. This is the standard way a LuaController initialises memory — it only sets a default the first time a key is missing, so it's safe to run after every restart without wiping anything out.

03

The reverse-lookup trick

The script needs to go both directions: name → id (to look up an item someone typed into a book), and id → name (to know what to put on a button, or tell an injector to fetch). The obvious way is two persisted tables, one each direction — but that stores every item's name twice in the saved data, and names are the single biggest thing in this table.

master.luaright after the mem block
local NAMES = {}
for nm, nid in pairs(mem.NAME_TO_ID) do NAMES[nid] = nm end

Only NAME_TO_ID is ever saved. NAMES is a plain local, rebuilt by looping over it at the top of every execution. Since the whole file re-runs on every event regardless, this loop rides along on a cost that's already being paid — it doesn't add a new one. What it buys back is real: every item name now exists once in the persisted table, not twice.

why this is safe

IDs are handed out once, in ensure_id, and never reused or removed. The inversion is therefore always complete and correct — there's no id that NAME_TO_ID knows about that NAMES could be missing or wrong for.

04

ensure_id / get_id

master.lua
local function get_id(name)
    return mem.NAME_TO_ID[name]
end

local function ensure_id(name)
    local id = mem.NAME_TO_ID[name]
    if not id then
        id = mem.NEXT_ID
        mem.NEXT_ID = id + 1
        mem.NAME_TO_ID[name] = id
        NAMES[id] = name
    end
    return id
end

get_id is a read-only lookup, used where a missing item should just mean "nothing to do." ensure_id is the only place a new id is ever created: it hands out the next free integer, writes it into the persisted NAME_TO_ID, and mirrors it into the local NAMES immediately so the current event can use the name right away without waiting for the next execution to rebuild the table.

05

parse_chest_string / build_chest_string

A single item can sit in several chests at once. Instead of a nested Lua table like {[3] = 64, [7] = 32} — which costs its own bytes for every level of structure once saved — ITEMS[id] holds one flat string: "3:64,7:32".

master.lua
local function parse_chest_string(s)
    local t = {}
    if s and s ~= "" then
        local pos = 1
        local len = #s
        while pos <= len do
            local colon = string.find(s, ":", pos, true)
            if not colon then break end
            local comma = string.find(s, ",", colon, true)
            local num_str = string.sub(s, pos, colon - 1)
            local qty_str
            if comma then
                qty_str = string.sub(s, colon + 1, comma - 1)
                pos = comma + 1
            else
                qty_str = string.sub(s, colon + 1)
                pos = len + 1
            end
            local num = tonumber(num_str)
            local qty = tonumber(qty_str)
            if num and qty then
                t[num] = qty
            end
        end
    end
    return t
end

local function build_chest_string(t)
    local parts = {}
    for num, qty in pairs(t) do
        table.insert(parts, num..":"..qty)
    end
    return table.concat(parts, ",")
end

parse_chest_string walks the string by hand — finding each : and , with string.find rather than a Lua pattern — and returns an ordinary {chest_num = qty} table. build_chest_string does the reverse: given that table, it produces the packed string to actually save. Everywhere else in the script only ever sees the unpacked table; the packed format exists purely at rest.

06

parse_slot_entry_string / build_slot_entry_string

The same idea, taken further, for SLOT_TRACKER. Each tracked entry used to be a small table with named fields — {slot = 4, count = 1, hits = 0}. Saved literally, those three field names repeat for every tracked item in every chest. Packed as "id:slot:count:hits", the field names never appear in storage — only the numbers do.

master.lua
local function parse_slot_entry_string(s)
    local t = {}
    if s and s ~= "" then
        local pos = 1
        local len = #s
        while pos <= len do
            local c1 = string.find(s, ":", pos, true)
            if not c1 then break end
            local c2 = string.find(s, ":", c1 + 1, true)
            if not c2 then break end
            local c3 = string.find(s, ":", c2 + 1, true)
            if not c3 then break end
            local comma = string.find(s, ",", c3, true)
            local id_str = string.sub(s, pos, c1 - 1)
            local slot_str = string.sub(s, c1 + 1, c2 - 1)
            local count_str = string.sub(s, c2 + 1, c3 - 1)
            local hits_str
            if comma then
                hits_str = string.sub(s, c3 + 1, comma - 1)
                pos = comma + 1
            else
                hits_str = string.sub(s, c3 + 1)
                pos = len + 1
            end
            local id = tonumber(id_str)
            if id then
                t[id] = {
                    slot = tonumber(slot_str),
                    count = tonumber(count_str),
                    hits = tonumber(hits_str),
                }
            end
        end
    end
    return t
end

local function build_slot_entry_string(t)
    local parts = {}
    for id, e in pairs(t) do
        table.insert(parts, id..":"..(e.slot or 0)..":"..(e.count or 0)..":"..(e.hits or 0))
    end
    return table.concat(parts, ",")
end

Four colon-delimited fields per entry (id, slot, count, hits) instead of three named table keys. Once unpacked, track_slot (§9) works with plain track.slot, track.count, track.hits field access — the packing is invisible to every caller.

get_item_chest_list

master.lua
local function get_item_chest_list(id)
    local list = {}
    local t = parse_chest_string(mem.ITEMS[id])
    for num, qty in pairs(t) do
        if qty and qty > 0 then
            table.insert(list, { num = num, qty = qty })
        end
    end
    return list
end

Turns an item's packed chest string into a plain array of {num=, qty=} entries — the shape both heal_item and the Take/book pull logic actually want to sort and iterate over.

update_oos

master.lua
local function update_oos(id, total_qty)
    if total_qty == 0 then
        if not mem.OOS_SET[id] then
            mem.OOS_SET[id] = true
            table.insert(mem.OOS, id)
        end
    elseif total_qty > 0 and mem.OOS_SET[id] then
        mem.OOS_SET[id] = nil
        for idx, oos_id in ipairs(mem.OOS) do
            if oos_id == id then
                table.remove(mem.OOS, idx)
                break
            end
        end
    end
end

OOS is the ordered list the stock screen actually paginates through. OOS_SET is a shadow table that turns "is this id already on the list?" into one lookup instead of a scan — the only reason the removal branch still has to loop is that removing from the middle of an array can't be done in O(1) in plain Lua.

09

heal_item

master.lua
local function heal_item(id)
    if mem.STATUS[id] == 2 then return end

    local total = mem.TOTALS[id]
    if not total or total == 0 then return end

    local partial_chests = {}
    for _, entry in ipairs(get_item_chest_list(id)) do
        local loose = entry.qty % 99
        if loose > 0 then
            table.insert(partial_chests, { num = entry.num, loose = loose })
        end
    end

    if #partial_chests >= 2 then
        table.sort(partial_chests, function(a, b) return a.num < b.num end)

        mem.HEAL_TARGET[id] = partial_chests[1].num

        for i = 2, #partial_chests do
            local sec = partial_chests[i]
            local inj_channel = "i" .. sec.num

            mem.EXPECT_HEAL[id] = (mem.EXPECT_HEAL[id] or 0) + sec.loose
            digiline_send("main_to_filter", { target = inj_channel, payload = { name = NAMES[id], count = sec.loose } })
        end
    end
end

Line 1 is a hard stop: an item already flagged STATUS == 2 — confirmed unstackable, typically a tool — never gets a consolidation attempt. Otherwise: 99 is the assumed max stack size, so entry.qty % 99 is whatever's "left over" in a chest beyond clean full stacks. Once two or more chests have loose leftovers, the lowest-numbered one becomes HEAL_TARGET, and every other chest's loose amount gets pulled — via the ordinary "i<num>" injector, relayed through the filter — toward it.

10

track_slot

The script never hardcodes which items stack. It watches behaviour: a stack bigger than one, ever, proves an item is stackable, permanently. Single copies landing in different slots without ever combining is read as proof it's not.

master.lua
local function track_slot(chest_num, id, delta, to_slot)
    if delta > 1 then
        mem.STATUS[id] = 1
        local raw = mem.SLOT_TRACKER[chest_num]
        if raw then
            local chest_tr = parse_slot_entry_string(raw)
            chest_tr[id] = nil
            mem.SLOT_TRACKER[chest_num] = next(chest_tr) and build_slot_entry_string(chest_tr) or nil
        end
        return
    end

    if mem.STATUS[id] == 1 or mem.STATUS[id] == 2 then return end

    local chest_tr = parse_slot_entry_string(mem.SLOT_TRACKER[chest_num])
    local track = chest_tr[id]

    if not track then
        chest_tr[id] = { slot = to_slot, count = delta, hits = 0 }
        mem.SLOT_TRACKER[chest_num] = build_slot_entry_string(chest_tr)
        return
    end

    if track.slot == to_slot then
        track.count = track.count + delta
        if track.count >= 2 then
            mem.STATUS[id] = 1
            chest_tr[id] = nil
            mem.SLOT_TRACKER[chest_num] = next(chest_tr) and build_slot_entry_string(chest_tr) or nil
        else
            mem.SLOT_TRACKER[chest_num] = build_slot_entry_string(chest_tr)
        end
        return
    end

    if track.count == 1 and delta == 1 then
        track.hits = track.hits + 1
        if track.hits >= 2 then
            mem.STATUS[id] = 2
            chest_tr[id] = nil
            mem.SLOT_TRACKER[chest_num] = next(chest_tr) and build_slot_entry_string(chest_tr) or nil
            return
        end
    end

    track.slot = to_slot
    track.count = delta
    mem.SLOT_TRACKER[chest_num] = build_slot_entry_string(chest_tr)
end

Read it as three cases in order. A real stack arrived (delta > 1): mark stackable for good, forget any tracking data for this id in this chest — there's nothing left to prove. Already decided (STATUS is 1 or 2): stop immediately, don't re-run the heuristic. Otherwise: this is a single-item delivery to a specific slot. If it's the first one seen, start tracking it. If a second single copy lands in the same slot, that's really a stack forming — mark stackable. If it lands in a different slot twice in a row, that's the unstackable signature — mark it and stop watching.

why the early exit matters

Without the STATUS[id] == 1 or == 2 check returning immediately, this whole heuristic would re-run on every single-item delivery for every item, forever — even ones already proven either way. It's the difference between paying this cost once per item, ever, and paying it on every event.

update_stock

The one function every chest report eventually reaches — the actual ledger.

master.lua
local function update_stock(chest_num, id, delta, action_type, to_slot)
    local t = parse_chest_string(mem.ITEMS[id])
    local current_in_chest = t[chest_num] or 0
    local new_in_chest = math.max(0, current_in_chest + delta)
    local actual_diff = new_in_chest - current_in_chest

    if delta > 0 then
        if mem.HEAL_INCOMING[id] and mem.HEAL_INCOMING[id] > 0 then
            local incoming = math.min(mem.HEAL_INCOMING[id], delta)
            mem.HEAL_INCOMING[id] = mem.HEAL_INCOMING[id] - incoming

            if mem.HEAL_TARGET[id] and chest_num > mem.HEAL_TARGET[id] then
                mem.STATUS[id] = 2
                mem.HEAL_TARGET[id] = nil
            end

            if mem.HEAL_INCOMING[id] <= 0 then
                mem.HEAL_INCOMING[id] = nil
                mem.HEAL_TARGET[id] = nil
            end
        end

        if delta > 1 then
            mem.STATUS[id] = 1
            if mem.HEAL_TARGET[id] then mem.HEAL_TARGET[id] = nil end
        end
    end

    if new_in_chest > 0 then
        t[chest_num] = new_in_chest
    else
        t[chest_num] = nil
    end

    local packed = build_chest_string(t)
    mem.ITEMS[id] = (packed ~= "") and packed or nil

    if to_slot then
        if delta > 0 then
            track_slot(chest_num, id, delta, to_slot)
        elseif delta < 0 then
            local raw = mem.SLOT_TRACKER[chest_num]
            if raw then
                local chest_tr = parse_slot_entry_string(raw)
                local tr = chest_tr[id]
                if tr and tr.slot == to_slot then
                    tr.count = math.max(0, tr.count + delta)
                    if tr.count == 0 then
                        chest_tr[id] = nil
                    end
                    mem.SLOT_TRACKER[chest_num] = next(chest_tr) and build_slot_entry_string(chest_tr) or nil
                end
            end
        end
    end

    mem.TOTALS[id] = math.max(0, (mem.TOTALS[id] or 0) + actual_diff)
    update_oos(id, mem.TOTALS[id])

    if delta < 0 and mem.PENDING_PULL[id] and mem.PENDING_PULL[id] > 0 then
        local taken = math.min(mem.PENDING_PULL[id], -actual_diff)
        mem.PENDING_PULL[id] = mem.PENDING_PULL[id] - taken
        if mem.PENDING_PULL[id] <= 0 then mem.PENDING_PULL[id] = nil end
    end

    local in_q = false
    for _, q_id in ipairs(mem.HEAL_QUEUE) do
        if q_id == id then in_q = true break end
    end
    if not in_q then
        table.insert(mem.HEAL_QUEUE, id)
    end

    mem.NEEDS_REDRAW = true
    schedule_tick(0.1)
end

In order: clamp — a chest's tracked quantity can never be pushed below zero, and actual_diff is the real change after that clamp, not the raw requested one. Bounce check — if a heal was in flight for this item and it landed in a chest numbered past the intended target, that's read as the item refusing to stack where expected, so it gets flagged unstackable right there. Absolute override — any stack bigger than one, seen anywhere, proves stackable outright and cancels any heal in progress. Re-pack and save the chest map. Feed the slot heuristic from §10, in either direction. Update the running total and the out-of-stock list. Release a pending-pull reservation if this take confirms one (see §15's callout). Queue for the heal pass if not already queued. And finally, mark the screen dirty and ask for a redraw next tick — never immediately, so several rapid reports in a row cost one redraw, not several.

start_search / step_search

Scanning every known item name against a query in one shot doesn't scale — a single event has a limited instruction budget. So it runs in chunks of SEARCH_CHUNK (400) items per tick.

master.lua
local function start_search()
    mem.SEARCH_IDX = {}
    mem.REQUEST_PAGE = 1
    mem.SEARCH_OVERFLOW = false
    mem.SEARCH_SCAN_POS = 0

    local q = mem.SEARCH_QUERY or ""
    mem.SEARCH_ACTIVE = (#q >= 2)
    if mem.SEARCH_ACTIVE then
        schedule_tick(0.1)
    end
end

local function step_search()
    if not mem.SEARCH_ACTIVE then return end

    local q_lower = string.lower(mem.SEARCH_QUERY or "")
    local total_items = mem.NEXT_ID - 1
    local last = math.min(mem.SEARCH_SCAN_POS + SEARCH_CHUNK, total_items)

    for id = mem.SEARCH_SCAN_POS + 1, last do
        local name = NAMES[id]
        if string.find(string.lower(name), q_lower, 1, true) then
            table.insert(mem.SEARCH_IDX, id)
            if #mem.SEARCH_IDX >= 100 then
                mem.SEARCH_OVERFLOW = true
                mem.SEARCH_ACTIVE = false
                mem.NEEDS_REDRAW = true
                return
            end
        end
    end

    mem.SEARCH_SCAN_POS = last
    if mem.SEARCH_SCAN_POS >= total_items then
        mem.SEARCH_ACTIVE = false
    end
    mem.NEEDS_REDRAW = true
end

start_search only actually activates for queries of two characters or more — anything shorter would match almost everything and isn't worth scanning for. step_search also hard-caps results at 100 matches, bailing out early with SEARCH_OVERFLOW set rather than building an unbounded results list.

draw_request_list

master.lua
local function draw_request_list()
    if mem.SEARCH_OVERFLOW then
        digiline_send(SCREEN_REQUEST,{
            {command="clear"},
            {command="set",width=10,height=6,fixed_size=true},
            {command="add",element="label",X=2,Y=3,label="Too many results (Min 2 chars)"}
        })
        return
    end

    local is_search = (mem.MODE == "search")
    local total_items = mem.NEXT_ID - 1
    local total = is_search and #mem.SEARCH_IDX or total_items
    local pages = math.max(1, math.ceil(total / ITEMS_PER_PAGE))
    if mem.REQUEST_PAGE > pages then mem.REQUEST_PAGE = pages end

    local start = (mem.REQUEST_PAGE - 1) * ITEMS_PER_PAGE + 1
    local finish = math.min(start + ITEMS_PER_PAGE - 1, total)

    local ui = {
        {command="clear"},
        {command="set",width=10,height=6,fixed_size=true},
        {command="add",element="label",X=0.3,Y=0.05,label="Unique Items: "..total_items},
        {command="add",element="field",X=0.3,Y=0.6,W=5,H=1,name="query",label="",value=mem.SEARCH_QUERY},
        {command="add",element="button",X=6,Y=0.4,W=1.8,H=0.7,name="btn_search",label="Search"},
        {command="add",element="button",X=8,Y=0.1,W=1.8,H=0.6,name="btn_home",label="Home"},
        {command="add",element="button",X=0.3,Y=6-BOTTOM_PADDING,W=2,H=0.6,name="btn_prev",label="< Prev"},
        {command="add",element="label",X=4.6,Y=6-BOTTOM_PADDING+0.1,label="Page "..mem.REQUEST_PAGE.."/"..pages},
        {command="add",element="button",X=10-2.3,Y=6-BOTTOM_PADDING,W=2,H=0.6,name="btn_next",label="Next >"},
    }

    if total == 0 then
        table.insert(ui, {command="add", element="label", X=3, Y=3, label="No Items"})
        digiline_send(SCREEN_REQUEST, ui)
        return
    end

    local draw_i = 0
    for i = start, finish do
        local id = is_search and mem.SEARCH_IDX[i] or i
        if id then
            local qty = mem.TOTALS[id] or 0
            if qty > 0 then
                local x = (draw_i % COLS) * (SIZE + GAP)
                local y = math.floor(draw_i / COLS) * (SIZE + GAP) + TOP_PADDING

                table.insert(ui, {
                    command = "add",
                    element = "item_image_button",
                    X = x, Y = y,
                    W = SIZE, H = SIZE,
                    item_name = NAMES[id],
                    name = "item_"..i,
                    label = "x"..qty
                })
                draw_i = draw_i + 1
            end
        end
    end

    digiline_send(SCREEN_REQUEST, ui)
end

One full formspec-style command list, built from scratch and sent in a single digiline_send — there's no partial-update path, since digiline touchscreens don't support one. Two details worth noticing: an item with TOTALS == 0 never gets a button at all (the if qty > 0 then guard) — the remaining buttons close the gap rather than leaving an empty slot; and draw_i, not the loop index i, is what positions each button on the grid, which is exactly what keeps that gap-closing working.

handle_chest_msg

master.lua
local function handle_chest_msg(channel, msg)
    if type(channel) ~= "string" or string.sub(channel, 1, 1) ~= "c" then return end

    local chest_num = tonumber(string.sub(channel, 2)) or 0
    local m = msg

    if type(m) == "table" then
        local action = m.action
        local stack = m.stack or m
        local name = ""
        local count = 1
        local to_slot = m.to_slot

        if type(stack) == "string" then
            local n, q
            local space = string.find(stack, " ", 1, true)
            if space then
                n = string.sub(stack, 1, space - 1)
                q = string.sub(stack, space + 1)
            else
                n = stack
            end
            name = n or stack
            count = tonumber(q) or 1
        elseif type(stack) == "table" then
            name = stack.name or ""
            count = tonumber(stack.count) or 1
            to_slot = to_slot or stack.to_slot
        end

        if name ~= "" and count > 0 then
            local id = ensure_id(name)
            if action == "put" or action == "tput" or action == "uput" then
                update_stock(chest_num, id, count, action, to_slot)
            elseif action == "take" or action == "ttake" or action == "utake" then
                update_stock(chest_num, id, -count, action, to_slot)
            end
        end
    end
end

This only ever fires for channels starting with "c" — the chest number is just the rest of the channel name, turned into a number. The stack can arrive either as a plain string ("itemname count") or a table with a name/count pair; both are handled. Anything that doesn't match — wrong channel, malformed message, unrecognised action — is silently ignored. There's no error path here on purpose: a chest report the script doesn't understand should do nothing, not crash the controller.

queue_book_order

A written book's order list looks like "default:cobble 12 , default:dirt 10". This walks the string entirely by hand — no Lua patterns — trimming spaces manually on both sides of each split.

master.lua
local function queue_book_order(text)
    local pos = 1
    local text_len = string.len(text)

    while pos <= text_len do
        local comma = string.find(text, ",", pos, true)
        local line
        if comma then
            line = string.sub(text, pos, comma - 1)
            pos = comma + 1
        else
            line = string.sub(text, pos, text_len)
            pos = text_len + 1
        end

        while string.sub(line, 1, 1) == " " do
            line = string.sub(line, 2)
        end
        while string.sub(line, -1) == " " do
            line = string.sub(line, 1, string.len(line) - 1)
        end

        if string.len(line) > 0 then
            local space = string.find(line, " ", 1, true)
            if space then
                local item = string.sub(line, 1, space - 1)
                local qty_str = string.sub(line, space + 1)

                while string.sub(qty_str, 1, 1) == " " do
                    qty_str = string.sub(qty_str, 2)
                end
                while string.sub(qty_str, -1) == " " do
                    qty_str = string.sub(qty_str, 1, string.len(qty_str) - 1)
                end

                local qty = tonumber(qty_str)
                if item and string.len(item) > 0 and qty and qty > 0 then
                    local id = mem.NAME_TO_ID[item]
                    local truly_available = (mem.TOTALS[id] or 0) - (mem.PENDING_PULL[id] or 0)
                    if id and truly_available >= qty then
                        table.insert(mem.BOOK_QUEUE, { name = item, count = qty })
                    end
                end
            end
        end
    end
end

The outer loop splits on commas, one order line at a time. Each line gets trimmed, then split again on the first space into an item name and a quantity string, which also gets trimmed before tonumber. A line only gets queued if the item is known and there's truly enough left — not just in TOTALS, but after subtracting whatever's already reserved by PENDING_PULL.

why PENDING_PULL exists

mem.TOTALS only updates once a chest's own take report comes back — after a pull has already been sent, not before. Checking raw TOTALS alone leaves a short window where a second order for the same item can pass the check against stock that's already spoken for. PENDING_PULL[id] is incremented the instant a pull is dispatched (§18) and released the instant the chest confirms it (§11) — closing that window with one more small number, not a table of names.

A line that fails either check is simply never queued — no error, no partial-fulfilment note. The book itself always comes back regardless of how many lines succeeded.

master.lua
if event.type == "interrupt" and event.iid == "tick" then
    mem.TICK_PENDING = false
    mem.TICK_COUNT = mem.TICK_COUNT + 1

    step_search()

    if mem.NEEDS_REDRAW then
        mem.NEEDS_REDRAW = false
        if not mem.SELECTED_ITEM then draw_request_screen() end
        draw_stock_screen()
    end

    if #mem.HEAL_QUEUE > 0 then
        local heal_id = table.remove(mem.HEAL_QUEUE, 1)
        heal_item(heal_id)
    end

    if #mem.BOOK_QUEUE > 0 then
        local line = table.remove(mem.BOOK_QUEUE, 1)
        local id = mem.NAME_TO_ID[line.name]
        if id then
            local chest_list = get_item_chest_list(id)
            table.sort(chest_list, function(a, b) return a.num > b.num end)
            local amount_needed = line.count
            for _, entry in ipairs(chest_list) do
                local take_qty = math.min(amount_needed, entry.qty)
                local inj_channel = "i" .. entry.num
                mem.EXPECT_USER[id] = (mem.EXPECT_USER[id] or 0) + take_qty
                mem.EXPECT_BOOK[id] = (mem.EXPECT_BOOK[id] or 0) + take_qty
                mem.PENDING_PULL[id] = (mem.PENDING_PULL[id] or 0) + take_qty
                digiline_send("main_to_filter", { target = inj_channel, payload = { name = line.name, count = take_qty } })
                amount_needed = amount_needed - take_qty
                if amount_needed <= 0 then break end
            end
        end
    end

    if mem.SEARCH_ACTIVE or #mem.HEAL_QUEUE > 0 or #mem.BOOK_QUEUE > 0 or mem.NEEDS_REDRAW then
        schedule_tick(0.4)
    end
end

The heartbeat. Each firing: advances search by one chunk, redraws whichever screen changed, drains exactly one entry each from the heal queue and the book queue — never more, so a big order can't spike a single event's cost — and reschedules itself only if there's genuinely still work pending. When nothing's left, it simply stops rescheduling rather than idling forever.

The book-queue branch pulls from the highest-numbered chest holding stock downward (a.num > b.num), tags the pull in three places at once — EXPECT_USER so the existing safety-buffer logic (§20) hands it off correctly, EXPECT_BOOK so the final-chest logic (§20) can tell it apart from a touchscreen delivery, and PENDING_PULL so a second order can't double-claim the same stock — and sends the pull itself through main_to_filter, since master isn't wired directly to the numbered injectors.

event.channel == "final"

master.lua
if event.channel == "final" then
    local msg = event.msg
    local name, qty = "", 0

    if type(msg) == "table" and msg.action then
        if msg.action == "take" or msg.action == "ttake" or msg.action == "utake" then
            return
        end
    end

    -- (name/qty parsing, identical shape to handle_chest_msg, omitted here for length)

    if name == "default:book_written" then
        if mem.BOOK_PENDING_RETURN > 0 then
            mem.BOOK_PENDING_RETURN = mem.BOOK_PENDING_RETURN - 1
        end
        digiline_send("final_book", name .. " " .. qty)
        return
    end

    if name ~= "" and qty > 0 then
        local id = mem.NAME_TO_ID[name]
        local book_amt = id and (mem.EXPECT_BOOK[id] or 0) or 0

        if book_amt > 0 then
            local take = math.min(book_amt, qty)
            mem.EXPECT_BOOK[id] = book_amt - take
            if mem.EXPECT_BOOK[id] <= 0 then mem.EXPECT_BOOK[id] = nil end
            digiline_send("final_book", name .. " " .. take)

            local leftover = qty - take
            if leftover > 0 then
                digiline_send("final_inj", name .. " " .. leftover)
            end
        else
            digiline_send("final_inj", name .. " " .. qty)
        end
    end
    return
end

A take report on this channel means an earlier ejection from this same chest is being echoed back — ignored immediately, or it would get reprocessed as a fresh arrival. Once parsed, there are exactly two outcomes: if the arriving item is the book itself, it goes straight out final_book, no further checks. Otherwise, EXPECT_BOOK decides the split — whatever portion of the arriving stack was reserved for a book order gets peeled off toward final_book first, and anything left over is treated as a touchscreen delivery and sent out final_inj.

Note both outbound sends here go directly to final_book/final_inj, not through main_to_filter — since master already receives this channel's reports directly, it's wired to reach those two injectors directly too, unlike the numbered storage injectors.

SIGNAL FILTER
24

The whole script

Deliberately the smallest file in the system. It holds no state between messages, uses no interrupts, and does exactly one thing.

signal_filter.luacomplete
if event.type == "digiline" then
    local ch = event.channel

    if type(ch) == "string" and string.sub(ch, 1, 1) == "c" then
        local is_overflow = false
        if type(event.msg) == "string" and event.msg == "toverflow" then
            is_overflow = true
        elseif type(event.msg) == "table" and event.msg.action == "toverflow" then
            is_overflow = true
        end

        if not is_overflow then
            digiline_send("filter_to_main", { ch = ch, data = event.msg })
        end
    end
end

Read top to bottom: only digiline events are handled at all — there's no tick, no program branch, nothing else in this file. Only channels starting with "c" are looked at; every other channel in the system — book, final, safety…, the two screens, main_to_filter — passes straight through this controller without triggering anything, because nothing here is listening for them. A toverflow message (a tube reporting it couldn't push an item anywhere) is filtered out rather than relayed, since it's noise master has no use for. Everything else gets repackaged as {ch=, data=} and sent to filter_to_main, immediately, in the same event — no batching, no delay.

why this can't loop

This controller listens on "c*" and speaks on exactly one channel, filter_to_main — and nothing in the system listens on filter_to_main except master. Since the channel it listens on and the channel it speaks on never overlap, there's no message this filter could ever send that would come back around and trigger itself again. That's a structural guarantee, not a matter of being careful with the code.

the tradeoff

Without an interrupt, this filter can't hold multiple messages and combine them into one batch — each chest report costs master one event, the same as if the chests were wired to master directly. What the filter still buys is the physical separation itself: master's own wiring never has to reach the whole chest array, only this one controller. If message volume ever became the bottleneck again, closing that gap would require bringing back a timed batch — which needs an interrupt, and was ruled out deliberately here in favor of having nothing that could misfire.

CLOSING
25

The memory budget

Mesecons caps a LuaController's saved mem table at 100,000 bytes by default. Cross it and the controller doesn't just refuse to save — it overheats. Every packing decision on this page exists to push more unique items under that same ceiling without changing what the system does from the outside.

choicesaves
integer ids instead of name strings as keysa full item name's length, on every table otherwise keyed by name
one persisted name table, one rebuilt locallyevery item name's length, a second time over
packed chest stringsnested-table overhead — one sub-table per chest, per item
packed slot-tracker stringsthree repeated field names, per tracked slot entry
STATUS memoizationnot bytes — instruction budget: skips re-running the stackability check forever, once decided
PENDING_PULLnot memory either — closes a real race window with one small number per reserved item, instead of a name-keyed table

None of it is visible from outside the controller. The touchscreen, the book, and the chests all behave exactly as if the data were stored the simple way — the packing only exists at the boundary between memory and everything else.
