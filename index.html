The Order Router

A walkthrough of the LuaController script running this storage system — how it tracks thousands of items in a chest array, fulfils requests from a touchscreen or a written book, and stays inside a 100,000-byte memory budget while doing it.

master.lua · mesecons_luacontroller · digilines
01

The system, at a glance

This is one script, running on one LuaController (master), plus a second, much smaller script running on a companion controller (signal filter) that sits between master and the chest array purely to keep master's message count down.

Master's job is to answer one question, over and over: which chest is this item in, and how much of it is there? — and to act on three ways of asking:

touchscreen→ Take→ book order→ queued pull→ final chest→ delivered

Everything the script knows is kept in mem — the one table mesecons persists for a LuaController between events. Every other variable, including entire functions, is rebuilt from nothing on every single event the controller receives. That one fact shapes almost every design decision below.

02

Persisted state

The first forty-odd lines are all the same shape: if not mem.X then mem.X = ... end. This is how a LuaController initialises its persistent memory — cheaply, and safely across restarts, since it only sets a default the first time a key doesn't exist yet.

master.luatop of file
if not mem.NAME_TO_ID then mem.NAME_TO_ID = {} end
if not mem.NEXT_ID then mem.NEXT_ID = 1 end
if not mem.TOTALS then mem.TOTALS = {} end
if not mem.ITEMS then mem.ITEMS = {} end
if not mem.STATUS then mem.STATUS = {} end
if not mem.SLOT_TRACKER then mem.SLOT_TRACKER = {} end
if not mem.OOS then mem.OOS = {} end
if not mem.OOS_SET then mem.OOS_SET = {} end
fieldwhat it holds
NAME_TO_IDevery item name seen so far, mapped to a small integer id
NEXT_IDthe next id to hand out — only ever counts up
TOTALSid → total quantity across every chest
ITEMSid → packed string of which chest holds how much
STATUSid → 1 (confirmed stackable) or 2 (confirmed unstackable)
SLOT_TRACKERper chest, a packed record of what's being watched for the stackability heuristic
OOS / OOS_SETthe out-of-stock list, plus a shadow set for instant membership checks

Everything is keyed by id, a small integer, rather than by the item's full name string. That single choice is what makes the rest of the memory-saving design possible — an integer key costs a few bytes; a string key like "technic:blue_energy_crystal" costs its full length, every time it appears.

03

The reverse-lookup trick

Somewhere the script needs to go both directions: name → id (to look up an item someone typed into a book), and id → name (to know what to actually put on a button, or tell an injector to fetch). The obvious way is to keep two persisted tables — one each direction. The catch: that stores every item's name twice in the saved data, and names are the single biggest thing in this whole table.

master.luaafter the mem block
local NAMES = {}
for nm, nid in pairs(mem.NAME_TO_ID) do NAMES[nid] = nm end

Only NAME_TO_ID is persisted. NAMES — the id → name direction — is a plain local, rebuilt from scratch by looping over NAME_TO_ID at the very top of every execution. Because a LuaController re-runs the whole file on every event anyway, this loop is just part of that same cost — it's not a new one. What it buys back is real: each item name is now stored exactly once in the persisted table, not twice.

why this is safe

IDs are handed out once, in ensure_id, and never reused or removed. That means the inversion is always complete and always correct — there's no case where NAMES[id] could be stale or missing for an id that NAME_TO_ID knows about.

04

Assigning item IDs

master.luaensure_id
local function ensure_id(name)
    local id = mem.NAME_TO_ID[name]
    if not id then
        id = mem.NEXT_ID
        mem.NEXT_ID = id + 1
        mem.NAME_TO_ID[name] = id
        NAMES[id] = name
    end
    return id
end

The first time a chest reports an item the script has never seen, it's given the next free integer and remembered permanently — in NAME_TO_ID for the saved copy, and in the local NAMES table so the current run can immediately use it too. Every other function that needs an id already knows it exists and just reads mem.NAME_TO_ID[name] directly.

05

Packing chest data into strings

A single item can sit in several chests at once. Storing that as a nested Lua table — {[3] = 64, [7] = 32} — works, but every level of table structure in the saved data costs its own bytes. Instead, ITEMS[id] holds one flat string: "3:64,7:32".

master.luaparse_chest_string / build_chest_string
local function parse_chest_string(s)
    local t = {}
    if s and s ~= "" then
        local pos = 1
        local len = #s
        while pos <= len do
            local colon = string.find(s, ":", pos, true)
            if not colon then break end
            local comma = string.find(s, ",", colon, true)
            local num_str = string.sub(s, pos, colon - 1)
            local qty_str
            if comma then
                qty_str = string.sub(s, colon + 1, comma - 1)
                pos = comma + 1
            else
                qty_str = string.sub(s, colon + 1)
                pos = len + 1
            end
            local num = tonumber(num_str)
            local qty = tonumber(qty_str)
            if num and qty then
                t[num] = qty
            end
        end
    end
    return t
end

Everywhere else in the script treats a chest map as a real Lua table — parse_chest_string unpacks the string into one, code does normal table operations on it, then build_chest_string flattens it back down before it's written to mem. The packed format only exists at rest; nothing downstream has to know about it.

06

The packed slot tracker

The same trick, taken further, for SLOT_TRACKER. Each tracked entry used to be a small table with named fields — {slot = 4, count = 1, hits = 0}. Saved literally, those three field names get repeated for every single tracked item, in every chest. Packed as "id:slot:count:hits", the field names never appear in storage at all — only the numbers do.

master.luaparse_slot_entry_string
local function parse_slot_entry_string(s)
    local t = {}
    if s and s ~= "" then
        local pos = 1
        local len = #s
        while pos <= len do
            local c1 = string.find(s, ":", pos, true)
            if not c1 then break end
            local c2 = string.find(s, ":", c1 + 1, true)
            if not c2 then break end
            local c3 = string.find(s, ":", c2 + 1, true)
            if not c3 then break end
            local comma = string.find(s, ",", c3, true)
            local id_str = string.sub(s, pos, c1 - 1)
            local slot_str = string.sub(s, c1 + 1, c2 - 1)
            local count_str = string.sub(s, c2 + 1, c3 - 1)
            local hits_str
            if comma then
                hits_str = string.sub(s, c3 + 1, comma - 1)
                pos = comma + 1
            else
                hits_str = string.sub(s, c3 + 1)
                pos = len + 1
            end
            local id = tonumber(id_str)
            if id then
                t[id] = {
                    slot = tonumber(slot_str),
                    count = tonumber(count_str),
                    hits = tonumber(hits_str),
                }
            end
        end
    end
    return t
end

Once unpacked into t[id] = {slot=, count=, hits=}, the calling code — track_slot — works with ordinary field access, same as before. The packing is invisible everywhere except the two functions that do it.

07

Out-of-stock bookkeeping

master.luaupdate_oos
local function update_oos(id, total_qty)
    if total_qty == 0 then
        if not mem.OOS_SET[id] then
            mem.OOS_SET[id] = true
            table.insert(mem.OOS, id)
        end
    elseif total_qty > 0 and mem.OOS_SET[id] then
        mem.OOS_SET[id] = nil
        for idx, oos_id in ipairs(mem.OOS) do
            if oos_id == id then
                table.remove(mem.OOS, idx)
                break
            end
        end
    end
end

OOS is an ordered list — it's what the stock screen actually paginates through. OOS_SET exists purely so "is this id already on the list?" is a single table lookup instead of a scan. The two small integer tables cost far less than the risk of scanning a long list on every stock change.

08

Consolidating loose stacks

If the same item ends up scattered as small, non-full stacks across several chests, heal_item quietly merges them — pulling the loose remainder out of every chest but one, and routing it toward the lowest-numbered chest that already has some.

master.luaheal_item
local function heal_item(id)
    if mem.STATUS[id] == 2 then return end

    local total = mem.TOTALS[id]
    if not total or total == 0 then return end

    local partial_chests = {}
    for _, entry in ipairs(get_item_chest_list(id)) do
        local loose = entry.qty % 99
        if loose > 0 then
            table.insert(partial_chests, { num = entry.num, loose = loose })
        end
    end

    if #partial_chests >= 2 then
        table.sort(partial_chests, function(a, b) return a.num < b.num end)
        mem.HEAL_TARGET[id] = partial_chests[1].num

        for i = 2, #partial_chests do
            local sec = partial_chests[i]
            local inj_channel = "i" .. sec.num
            mem.EXPECT_HEAL[id] = (mem.EXPECT_HEAL[id] or 0) + sec.loose
            digiline_send("main_to_filter", { target = inj_channel, payload = { name = NAMES[id], count = sec.loose } })
        end
    end
end

The very first line is a hard stop: an item already flagged STATUS == 2 (confirmed unstackable — a tool, typically) never gets a consolidation attempt, since there's nothing to consolidate. 99 is the stack size the whole system assumes; anything beyond a clean multiple of it, per chest, counts as "loose" and becomes a candidate to move.

09

Detecting unstackable items

The script never hardcodes which items stack and which don't — it works it out by watching behaviour. If a stack of more than one of an item is ever seen, that's proof it's stackable, permanently. If single copies keep landing in different slots of the same chest without ever combining, that's read as proof it's not.

master.luatrack_slot
local function track_slot(chest_num, id, delta, to_slot)
    if delta > 1 then
        mem.STATUS[id] = 1  -- saw a real stack: definitely stackable
        -- ...clears any tracking data for this id, nothing left to prove
        return
    end

    if mem.STATUS[id] == 1 or mem.STATUS[id] == 2 then return end
    -- already decided either way — don't keep re-checking

    -- ...otherwise: watch where single copies land. two hits in two
    -- different slots, never combining, is read as "unstackable"
end
why this matters for memory

Once STATUS[id] is set, the heuristic stops running for that item — forever. Without that early exit, every single-item delivery would re-run the slot-watching logic on every event, for every item, indefinitely.

10

The ledger: update_stock

This is the one function every chest report eventually calls, and everything above exists to serve it. Given a chest number, an item id, and a signed quantity change, it does five things in order:

  1. Unpacks that item's chest map, applies the change, clamps it so a chest can never go negative, and re-packs it.
  2. If the change is a put, checks whether it was expected as part of a heal-in-progress — and if it landed somewhere past the intended target chest, that's read as a bounce, and the item gets flagged unstackable right there.
  3. Feeds the same put/take into the slot-watching heuristic from the section above.
  4. Updates the running total for that item, and the out-of-stock list.
  5. If this take closes out a pull that was reserved via PENDING_PULL, releases that reservation.

It finishes by marking the screen dirty and asking for a redraw on the next tick — never redrawing immediately, so that several rapid chest reports in a row only cost one redraw, not several.

11

Paged, non-blocking search

Scanning every known item name against a query, in one go, doesn't scale once the catalogue gets large — a single event has a limited instruction budget, and a full scan could blow through it. So the search doesn't run in one shot: it runs in chunks of 400 items per tick, tracked by SEARCH_SCAN_POS, and only re-schedules itself while there's still ground to cover.

master.luastep_search
local function step_search()
    if not mem.SEARCH_ACTIVE then return end

    local q_lower = string.lower(mem.SEARCH_QUERY or "")
    local total_items = mem.NEXT_ID - 1
    local last = math.min(mem.SEARCH_SCAN_POS + SEARCH_CHUNK, total_items)

    for id = mem.SEARCH_SCAN_POS + 1, last do
        local name = NAMES[id]
        if string.find(string.lower(name), q_lower, 1, true) then
            table.insert(mem.SEARCH_IDX, id)
            if #mem.SEARCH_IDX >= 100 then
                mem.SEARCH_OVERFLOW = true
                mem.SEARCH_ACTIVE = false
                return
            end
        end
    end

    mem.SEARCH_SCAN_POS = last
    if mem.SEARCH_SCAN_POS >= total_items then
        mem.SEARCH_ACTIVE = false
    end
end

A search is also capped at 100 matches — past that it stops early and the request screen shows a plain "too many results" message instead of a half-built page.

12

Drawing the two screens

draw_request_list and draw_stock_screen both build a full formspec-style command list from scratch and send it in one digiline_send — there's no partial-update path, since digiline touchscreens don't support one. A small but easy-to-miss detail: draw_request_list skips any item whose TOTALS is exactly zero, so an out-of-stock item simply never gets a button — the remaining buttons close the gap rather than leaving a hole.

The unique-item count shown above the search field is just mem.NEXT_ID - 1 — since ids are never reused, that's always exactly the number of distinct items the system has ever registered.

13

Reading a chest report

handle_chest_msg is where a raw digiline message from a numbered chest — arriving batched through the filter — turns into a call to update_stock. It only ever looks at channels starting with "c", and only acts on put/tput/uput and take/ttake/utake actions; anything else is silently ignored, which is deliberate — there's no error path here, a malformed or unexpected message just does nothing rather than crashing the script.

14

Parsing an order book

A written book's order list looks like "default:cobble 12 , default:dirt 10" — comma-separated lines, each an item name and a quantity separated by whitespace. queue_book_order walks the string by hand rather than with a pattern, trimming spaces manually on both sides of the split, the same technique used for the item/quantity split itself.

master.luaqueue_book_order (excerpt)
local qty = tonumber(qty_str)
if item and string.len(item) > 0 and qty and qty > 0 then
    local id = mem.NAME_TO_ID[item]
    local truly_available = (mem.TOTALS[id] or 0) - (mem.PENDING_PULL[id] or 0)
    if id and truly_available >= qty then
        table.insert(mem.BOOK_QUEUE, { name = item, count = qty })
    end
end
the reason for PENDING_PULL

mem.TOTALS only updates once a chest's own take report comes back — which happens after a pull has already been sent, not before. Checking raw TOTALS alone leaves a short window where a second order for the same item can pass the check against stock that's already spoken for. PENDING_PULL[id] is incremented the instant a pull is dispatched and released the instant the chest confirms it — closing that window without needing a table of names, just one more small number per reserved item.

A line that fails the check is simply never queued — no error, no partial fulfilment note. The book itself is always sent back regardless, whether every line succeeded, some did, or none did.

15

The event loop

Everything above is just function definitions — nothing runs until an event arrives. The bottom of the script is a sequence of if event.type == ... blocks, each independent, each only doing something if its condition matches.

program

Fires once when the controller is (re)programmed. Resets the tick-pending flag — a safety net in case an edit happened mid-cycle — and draws both screens once, the very first time, so they're not blank before anything else has happened.

interrupt / tick

The heartbeat. On each firing it: advances the search by one chunk, redraws either screen if something changed, drains one entry each from the heal queue and the book queue, and — only if there's still real work left to do — schedules itself again. When there's nothing left pending, the tick simply stops rescheduling, rather than running forever in the background.

digiline / filter_to_main

Storage-chest reports arrive here, already relayed by the filter. Each one is handed straight to handle_chest_msg.

digiline / book

A written book has reached the intake tube. If its meta.owner is in ALLOWED_BOOK_PLAYERS, its meta.text gets parsed and queued; either way, a return is recorded so the book itself comes back once processing settles — permission or no permission, missing items or not.

digiline / final

Something has landed in the final chest. If it's the book itself, it goes straight back out. Otherwise, whatever portion of it was reserved for a book order (tracked in EXPECT_BOOK) is separated out and sent one way; anything left over is treated as a touchscreen delivery and sent the other.

digiline / safety…

The original delivery path, unchanged by any of the book-ordering work: an item has arrived at a safety buffer, and whatever's currently expected there (EXPECT_USER) is handed off first, with any surplus routed back for healing.

digiline / screen_request, screen_stock

Button presses from the two touchscreens — paging, searching, selecting an item, confirming a Take.

16

The signal filter

The companion script is deliberately tiny: it only relays "c"-prefixed chest channels up to master, and only ever sends to one channel, filter_to_main, that nothing else listens on. It holds no state of its own between messages. That combination — one input pattern, one fixed output channel, nothing remembered — is what makes it structurally impossible for the filter to echo a message back into itself.

17

Staying inside the memory budget

Mesecons imposes a hard ceiling on how large a LuaController's saved mem table is allowed to get — 100,000 bytes by default. Cross it, and the controller doesn't just refuse to save; it overheats. Every design choice on this page — packed strings instead of nested tables, one name table instead of two, integer ids instead of string keys everywhere — exists to push more unique items under that same ceiling.

choicesaves
integer ids, not name strings, as keysa full item name's length, on every table that would otherwise be keyed by name
one persisted name table, one rebuilt locallyevery item name's length, a second time
packed chest stringsthe nested-table overhead of one sub-table per chest, per item
packed slot-tracker stringsthree repeated field names, per tracked slot entry
STATUS memoizationnot bytes — instruction budget: skips re-running the stackability check forever, once decided

None of this changes what the system does. Every one of these is invisible from the outside — the touchscreen, the book, and the chests all behave exactly as if the data were stored the simple way. The packing only exists at the boundary between memory and everything else.
